# Native goals, plan mode and skill completion

## Prerequisites / Setup

- Use an app-server supporting `thread/goal/get`, `thread/goal/set`, and `thread/goal/clear`.
- Open an existing thread and install at least one enabled skill.

## Actions and Expected Results

1. Open **+ → Plan mode**. Toggle it and confirm the Plan chip appears without sending a message. Select the chip to return to default mode.
2. Type a skill name after `/` and select it: a skill chip appears and the completion token is removed. Disabled skills are absent; at most 20 suggestions appear.
3. In a disposable fixture without matching skills, submit each of `/prompts`, `/presets`, `/history`, `/help`, `/review`, `/compact`, `/diff`, `/processes`, `/goal` and `/plan`. Expect the normal submit payload to contain the exact text and no command-driven dialog or mode change.
4. In an existing thread without a goal, confirm there is no Goal chip or empty row. Enter a message draft, open **+ → Goal…**, and confirm a dialog titled **Goal settings** opens at the same size as Settings with the objective focused. Use **Cancel**, Escape, or **Close dialog** and verify the draft is intact and focus returns to **+**. Open the dialog again, save an objective and status, and reload to verify they persist.
5. Open the status picker and press Escape twice. The first press closes the picker, and the second closes Goal settings. Reopen Goal settings, edit status, and clear the goal. While a save or clear is pending, verify Close, Cancel, and Escape keep the dialog open. The returned server state is reflected on success. A failed save or clear keeps the editor open and displays an error.
6. Switch threads while a goal load/save is pending. The old response must not overwrite the new thread's panel. Emit a Goal update during a turn and verify that the status and usage update in the panel. Emit a Goal clear and verify that the summary disappears.
7. In light and dark themes at 1280×900, 768×1024, and 375×812, open Goal settings from the inline, full-screen, and minimized composers. Check that the heading has 8px above and below it, aligns with the body text, and is vertically centered with the close button. The objective should fill the width and the height left by the status, usage, any error, and the actions. Check that `Status: active` and `Status: usage limited` each fit on one line and that the options open above the picker.
8. Save an active goal with a distinctive first line and enough lines to scroll in the objective field. Enable **+ → Plan mode** and **+ → Queue mode**. Verify that **Goal: active** sits on the same row as **Plan** and **Queue** in the normal and full-screen composer. Hover over the Goal chip and inspect its accessible name in DevTools. Verify the chip text and accessible name are both **Goal: active**, and that hovering never reveals the objective.
9. Click the chip or focus it and press Enter. In **Goal settings**, verify that the objective field receives focus, scroll to the last line, and edit and save the objective. Reopen settings to verify the edit. Close settings using Cancel, Escape, or **Close dialog** and verify focus returns to the chip in the current composer mode. Minimize the composer and repeat opening and closing settings from the remaining Goal chip. Verify that the composer stays minimized.
10. Complete the goal via the app server or select `complete` in Goal settings and save. Verify the chip reads **Goal: completed**. Repeat with the other statuses and verify **Goal: paused**, **Goal: blocked**, **Goal: usage limited**, and **Goal: budget limited**. Clear the goal and confirm the chip disappears. Confirm Goal… is absent in a new, uncreated conversation.
11. Inspect Goal requests. Opening or closing the menu or editor and completing a turn add no Goal reads. Opening a different thread or reconnecting loads the selected Goal. Switch threads while editing and confirm that the previous editor closes and late responses cannot restore it. For tab indicators, follow [Background conversations, Goals, and pending requests](../thread-loading-state/thread-titles-without-generation.md#background-conversations-goals-and-pending-requests).
12. In light and dark themes, complete a Goal and keep that conversation selected. Use a test app-server or browser RPC fixture to make the next `thread/goal/get` return an error, then reconnect. Verify exactly one Goal read, the **Goal: completed** chip remains visible, and **Goal settings** shows the error and the retained objective. Restore successful Goal reads and reconnect again. Verify the error disappears and the chip reflects the returned status. Return an explicit `goal: null` on the next reconnect and verify the chip disappears. Remove the injected response after testing.
13. With an existing goal containing several dozen lines, open Goal settings and use DevTools to reduce the viewport to 375×250. Scroll within the objective to edit the last line. Open the status picker and verify its options scroll above the trigger. Reject the next save using the test app-server or RPC fixture, then scroll the dialog body to reach the usage, error, and **Clear goal**, **Cancel**, and **Save goal** buttons. Cancel and verify focus returns to the Goal chip. Restore the viewport and the successful save response after testing.
14. On a mobile device, open Goal settings and tap the objective to bring up the software keyboard. With the keyboard open, scroll the dialog to its actions. Verify the dialog and actions fit in the visible portion of the screen. Open the status picker and verify its menu fits above the trigger. Cancel the changes and confirm focus returns to the Goal chip.
15. Open two disposable threads on the same App Server ID. In the first, enter an objective with multiple lines, a blank line, and an indented line. Select **Save as template**, enter a unique name, and click **Save template**. Close Goal settings with **Cancel**. In the second thread, open Goal settings, select a status, and then select the saved name under **Saved templates**. Verify the objective preserves line breaks and indentation and the selected status stays visible. Append a line, click **Save goal**, then reopen Goal settings and verify the edited objective and status were applied. Open **Saved templates** and select the same name again. Confirm the stored body still matches the original. Click **Cancel** and reopen Goal settings. The edited objective and status should still be applied.
16. Repeat the template flow in light and dark themes at 1280×900, 768×1024, and 375×812. Verify the name input, template list, and confirmation controls are readable and fit at each width. Try saving different text under the same name. Verify the confirmation displays the existing name, **Use a different name** allows you to save a second template, and **Overwrite template** replaces the named entry after confirmation. Select **Delete** for one entry and verify the confirmation shows its name. Choose **Keep template** first, then reopen confirmation and choose **Delete template**. The other entry and any applied Goals should still be available.
17. With DevTools Network open, reload, switch threads, and open Goal settings. Verify zero `goal-templates/list` requests across these actions and exactly one per opening of **Saved templates**. Make the next list or save request fail using a browser RPC fixture. Verify the dialog displays the error and retains the draft. Hold a list request, switch threads or invalidate the connection, and release the response. Verify the old list does not appear. Restore successful responses afterward.
18. Open a fresh browser on the same App Server ID and load **Saved templates** in another project. Verify the saved entry is available. Restart the WebUI backend with the same ID and verify it is still available. Start a test backend with a different App Server ID using the same data root and verify the original ID's templates are absent.

## Automated Regression

After building, run `APPROVED_DIST_ROOT=. node scripts/test-composer-fullscreen.cjs` and `APPROVED_DIST_ROOT=. node scripts/test-composer-collapse.cjs` against `http://127.0.0.1:4173`. Set `PLAYWRIGHT_CHANNEL=chrome` to use an installed Google Chrome. The fixtures check the Goal labels, the Plan and Queue row, dialog layout, status selection, and focus restoration across all three composer modes. The full-screen fixture appends a final line, saves the changed objective and status, reopens the saved Goal, and checks body scrolling after a rejected save at 375×250. It also simulates a keyboard leaving a 250px visual viewport inside the 375×812 layout. The minimized fixture simulates a browser that activates the chip without focusing it first. Dialog screenshots are saved as `output/playwright/goal-settings-*.png` alongside the composer reports.

Run `APPROVED_DIST_ROOT=. node scripts/test-goal-templates.cjs` at the same URL to cover saving, cross-thread reuse, editing, Cancel, duplicate names, deletion, rejected requests, and stale responses. Run `pnpm run test:integration:fixture` after building to verify App Server ID isolation, restart persistence, concurrent saves, overwrite, and deletion through the real WebUI bridge.

## Performance Audit

The chip renders one status label from the selected Goal in memory. The settings form mounts only while the dialog is open, and CSS sizes the objective and scrollable body. The status menu reuses the dropdown's positioning and scroll listeners while open. Playwright fixtures measured zero extra API requests from status notifications and opening or closing settings in all three composer modes, in both themes at 1280×900, 375×812, and 768×1024. Saving or clearing uses one Goal mutation each.

Opening a conversation or reconnecting reads one Goal for the selected conversation. The panel and tab indicators share that state and use the existing notification stream for changes. Goal events skip the conversation list and history refresh queue. Pending request events reuse the existing approval state and update the indicators locally. Browser fixture request counts confirmed zero additional API calls for Goal completion and pending request notifications in both themes. Turn outcomes retain their existing history synchronization and perform zero Goal reads. State is scoped to the selected conversation, turn correlation retains up to 64 entries, and stale reads are discarded after navigation or a newer event. The feature adds no polling, blocking I/O, or cross-thread fanout. Payload sizes are unchanged. Completion searches the installed skills locally, sorts matching skills, and renders at most 20 rows. Search cost is O(n log n) in the worst case for n matching skills.

The template fixture checks zero template list requests at startup, on thread selection, when Goal settings opens, and when saving a template. Opening **Saved templates** reads one backend JSON file and returns its entries. Selecting a template is local. Each save or deletion updates the same file through the existing asynchronous lock and atomic write. A duplicate name requires a second save request only after confirmation. The list is discarded when the panel closes or its thread or connection changes. List payload and file update costs scale with the total template text. Template operations have no upstream App Server calls.

## Rollback / Cleanup

Clear the temporary goal, disable Plan and Queue, remove temporary drafts and skill attachments, and restore the original theme.
Delete any temporary templates from **Saved templates** and stop any test backend started with a different App Server ID.
