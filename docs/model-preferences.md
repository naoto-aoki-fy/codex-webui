# Backend model preferences

Global composer preferences live in `codexapp-model-preferences.json` under the
backend's profile-scoped `CODEX_HOME`. The legacy profile uses `CODEX_HOME`
directly; named Connection Profiles use the existing hashed
`codexapp-profiles/<hash>/` directory. This is WebUI state on the backend host,
independent of the external Codex app-server's filesystem and native config.
No database or credentials are required to read preferences.

## State and defaults

Schema version 1 stores a monotonic revision,
`preferred` settings, `lastUsed` settings, per-provider/model reasoning choices,
and model usage entries. Settings contain provider ID, model ID, reasoning effort
(including an explicitly unspecified empty string), and collaboration mode.
Usage keys are JSON-encoded `[providerId, modelId]` tuples to avoid collisions,
including IDs containing `/`. Entries also include the two IDs explicitly.

`lastUsed` means the last successfully acknowledged `turn/start`, not the last
selector interaction or a completed response. New conversations restore it ahead
of an unused `preferred` choice. Before the first accepted turn, explicitly
selected `preferred` settings supply the default. An unsent Home selection
remains responsive in that browser and leaves usage counts unchanged.
Per-model effort changes are saved as individual patches. An accepted turn saves
the effective submitted effort and mode alongside the model.

Existing per-thread model choices, explicit-selection guards, collaboration modes,
and native thread restoration retain their existing behavior. Thread-specific
browser storage remains profile-scoped; it is not a second global preference
store. Shared updates do not replace explicit choices in existing conversations
or another browser's actively edited Home draft. Starting a new conversation or returning to Home adopts the shared default. Home resolves its
collaboration mode separately from the sidebar-selected thread.

Unavailable saved Home models/providers use the catalog/config fallback and show
a notice; refreshing the catalog restores a saved model if it returns. Fallbacks
do not rewrite saved preferences. Existing threads retain their provider guard;
changing providers still requires Portable Fork. Unsupported effort and
collaboration values resolve to supported UI defaults without rewriting storage.

These are **current preferences**, never evidence for historical response
metadata (CAP-003). No historical generation metadata is synthesized or modified.
Fork and Revert (CAP-001) and Portable Fork (CAP-002) are unchanged.

## API and synchronization

Methods use the existing authenticated `POST /codex-api/rpc` envelope:

| Method | Parameters | Result |
| --- | --- | --- |
| `model-preferences/read` | none | Current versioned snapshot and Connection Profile |
| `model-preferences/update` | `{ preferred?: ModelSettings, reasoning?: { providerId, modelId, effort } }` | Snapshot after field patches |
| `turn/start` | Existing native turn parameters | Existing turn result; backend records usage after acknowledgment |

There is deliberately no browser-callable counter increment: acceptance of
`turn/start` is the usage-recording endpoint. Usage currently covers acknowledged WebUI `turn/start` calls. Native queued or
external turns without that acknowledgment are not reconstructed from history.
Provider identity comes from the
backend's thread/start, resume or read result, not a browser assertion. A bounded
1,000-thread metadata cache normally avoids an extra read. On a cache miss, a
metadata-only thread read resolves provider identity; the backend never guesses
another provider. Collaboration-mode request overrides take precedence. UTC
`lastUsedAt` timestamps are generated by the backend and counts are incremented
under the storage lock. A bounded 256-turn ledger suppresses duplicate recording
of the same accepted thread/turn identity; it is not a general turn retry API.

The existing WebSocket/SSE stream carries `model-preferences/changed` snapshots.
Clients reject older revisions, coalesce initialization/reconnect reads, serialize
their own writes, and preserve pending effort edits through intermediate replies.
No polling is added. Separate backend processes sharing a state directory have
safe writes, but immediate push delivery is scoped to each backend process;
clients of another process reconcile on reconnect/reload.

## Atomic persistence and recovery

The dedicated store reuses `codexGlobalState.ts`'s canonical-path resolution,
per-path mutation queue, `proper-lockfile` cross-process lock, mode-preserving
private temporary file, fsync and atomic rename. Patches read current disk state
inside the lock, so concurrent clients cannot lose independent effort changes or
usage increments. Competing writes to the same preference intentionally use the
last serialized write; clients do not upload whole stale snapshots.

Missing files and malformed JSON/fields yield safe empty or sanitized state.
Explicit future schema versions fail closed and preserve the file. The malformed
JSON recovery option applies only to the dedicated preference file; existing
Codex global-state callers retain strict parsing. Filesystem/permission failures
are surfaced instead of being treated as missing data.

If persistence or provider resolution fails after turn acceptance, the accepted
turn still succeeds. The backend logs the failure and sends a
`model-preferences/error` notification. The UI displays a synchronization error
with a retry action. Retrying refreshes preferences, never replays a turn. This
can leave that turn absent from usage history; there is no durable acceptance
outbox or cross-service transaction. Connection outages also cannot establish
acceptance for turns with an unknown outcome, so those are not counted here.

## Performance audit

Steady-state startup adds one preference read, coalesced across concurrent callers.
Fresh profiles also use that single read and display catalog defaults until
preferences are set. Ordinary model refresh and navigation use the loaded
snapshot. Reconnects read once per concurrent refresh window. Each explicit
global choice or effort patch adds one write. An accepted
turn writes within its existing RPC and broadcasts once without a follow-up HTTP
request per browser. Preference notifications do not schedule thread/history reads.

All filesystem work is asynchronous. The existing cross-process lock can delay
acknowledgment during contention; retaining acceptance success on storage failure
avoids a duplicate-turn retry hazard. Decode/serialize and notification payload
sizes scale with distinct models, not message history. The accepted-turn ledger
and thread-identity cache are bounded. No catalog cache invalidation is introduced;
preferences and catalog availability remain separate, reactive inputs. Live
provider latency and multi-device network timings are not measured by fixture tests.


## Verification

Automated coverage includes storage recreation/restart, concurrent clients, profile
and provider isolation, exact UTC counts/timestamps, duplicate recording, missing
and corrupt files, future schemas, frontend restoration and
Home/thread isolation, notification ordering, pending writes, reconnects, and
accepted-turn persistence failures. The full unit suite also exercises protected
fork/transfer and historical generation-metadata behavior.

Browser fixture evidence: `http://127.0.0.1:4173/`, viewport **1440 × 1000**.
Assertions passed for B/high/Plan restoration over stale local A after reload,
actual selector order B then A, one preference read per normal initialization,
light/dark themes, storage failure/retry, and unavailable-model fallback preserving
the saved preference. No page errors occurred. These fixtures do not validate live
provider turns or authentication. Screenshot/report paths (local, untracked):

- `output/playwright/model-preferences-light.png`

one normal initialization preference read. Preference notifications do not add
thread/history reads. The production frontend entry is 487.16 kB (155.17 kB gzip), and the CLI bundle
is 209.15 KB. These are resulting sizes, not a before/after performance baseline; provider latency and real-device timing remain unmeasured.
